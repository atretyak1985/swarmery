# ADR 0001 — Дефолти агентів живуть в апстрімі; проєкт звужує їх, але не форкає

**Статус:** прийнято
**Дата:** 2026-09-07
**Контекст задачі:** `2026-09-07-unblock-delegated-agent-runs`, фаза 4 (SC-7, SC-10)

---

## Контекст

Ретроспектива вікна 18–31.08 показала, що делеговані виконавці не дописували роботу:
`implementation-agent` — error rate 80%, `design-implementer` — 100%. Розбір причин
знайшов **дві незалежні системи worktree-ізоляції**, з яких компенсації має тільки одна.

| Система | Де ріже | Компенсації |
|---|---|---|
| демон swarmery | `~/.swarmery/worktrees` (`tools/swarmery/internal/worktree/worktree.go`, `DefaultRoot`) | позичання phase-доку (`internal/worktree/plandoc.go`, `PlanDocDir = ".swarmery/plan"`), позичання `node_modules`/`.venv` символьними лінками (`internal/phaserun/prompt.go`), REPOSITORY-нота з переводом шляхів (там само) |
| Agent tool у Claude Code | `<project>/.claude/worktrees/agent-*`, вмикається ключем `isolation:` у frontmatter агента | **жодних** |

Заблоковані прогони вікна відбувалися в другій системі. Звідси `ERR_MODULE_NOT_FOUND`,
`FileNotFoundError` і відмови «читай копію доку в worktree» — усе те, від чого перша
система свої worktree вже захищає.

Ключ `isolation: worktree` стоїть рівно у двох агентів апстріму:
`plugins/core/agents/implementation-agent.md` і `plugins/core/agents/test-writer.md`.
У `plugins/design-pack/agents/design-implementer.md` цього ключа немає взагалі — отже
його 100% має інше джерело, і «полагодити його разом з ізоляцією» неможливо; це окреме
розслідування, а не наслідок цього ADR.

Звідси постало питання, яке цей ADR закриває: **де змінювати `isolation`** — глобально
в апстрімі чи форком у проєкті?

## Рішення

**Дефолти агентів живуть в апстрімі (`plugins/**/agents/*.md`). Проєкт може їх звузити,
але не форкати руками.**

Конкретно:

1. Проєкт оголошує звуження декларативно, у власному `.claude/settings.json`:

   ```json
   "swarmery": {
     "agents": { "implementation-agent": { "isolation": "none" } }
   }
   ```

   Єдиний ключ, який тут можна перевизначити, — `isolation`; допустимі значення `none`
   і `worktree`. Будь-яке інше значення — помилка з поясненням, ніколи не тихе
   ігнорування: тихо проігнорована ізоляція не відрізняється від робочої доти, доки
   агент не запише файл не в те дерево.

2. `swarmery agents sync` **генерує** `.claude/agents/<name>.md` — побайтову копію
   апстрім-файла, у якій змінено рівно один ключ frontmatter, плюс блок походження
   (`generated_by`, `source`, `source_sha`, `generated_at`) і рядок-попередження на
   початку тіла.

3. `swarmery agents sync --check` нічого не пише і **виходить кодом 1**, коли
   `source_sha` згенерованого файла розійшовся з поточним апстрімом, коли файл ще не
   згенеровано, або коли файл не має штампа `generated_by` (тобто написаний руками).

4. **Будь-який файл у `.claude/agents/` проєкту — або згенерований, або дефект.**
   Виняток лишається один: агент, який справді унікальний для проєкту й ніколи не
   існував в апстрімі (див. `docs/EXTENDING.md`, «правило градації»).

## Чому саме так

`isolation` резолвить **Claude Code**, а не swarmery, і робить це з frontmatter
агентського файла. Точки входу в цей резолвер у демона немає. Штатний спосіб перекрити
плагінного агента — файл із тим самим `name:` у `.claude/agents/` проєкту, і він
перекриває агента **цілком**, а не по ключу.

Тобто «звузити один ключ без форку» декларативно неможливо. Але можна зробити форк
**генерованим**: тоді дрейф стає не питанням дисципліни, а питанням коду виходу.

## Розглянуті альтернативи

| Альтернатива | Чому відкинута |
|---|---|
| **Глобально прибрати `isolation: worktree` в апстрімі** | Радіус — усі 11 неархівованих проєктів машини, при **непідтвердженій** причині. Ізоляція могла бути не причиною 80%, а лише корелятом; глобальна зміна знищила б можливість це перевірити й водночас забрала б ізоляцію в проєктів, які на неї покладаються. |
| **Рукописний форк агента в `.claude/agents/`** | Дрейф. Файл на 200+ рядків, скопійований заради одного ключа, розходиться з апстрімом мовчки й назавжди — це рівно та «fork-and-sync rot», яку `docs/EXTENDING.md` існує щоб усунути. |
| **Нове поле в `.claude/project.json` замість `settings.json`** | `project.json` — це flavor-конфіг продукту (репозиторії, домешні терміни, стек). Ізоляція агента — конфіг системи агентів, і `settings.json` уже несе блок `swarmery` (напр. `claudeAccount`), тож форма впізнавана без нової схеми. |
| **Розширити `internal/provision`** | Інша відповідальність: `provision` володіє user-level `settings.json` і свіжістю плагінів (`internal/provision/service.go`). Генерація project-level оверрайдів — окремий пакет `internal/agentsync`. |

## Наслідки

**Обов'язкове:**

- Генератор і `--check` — частина контракту, не зручність. Проєкт, який оголосив
  `swarmery.agents`, зобов'язаний тримати згенерований файл у git разом із
  `settings.json`, щоб стан був відтворюваним із чистого клону.
- Рукописний файл у `.claude/agents/`, що дублює апстрім-агента, вважається дефектом і
  повідомляється `--check` як `handwritten fork`.
- Зміна дефолту в апстрімі більше не «тихо проходить» повз проєкти-пілоти: `--check`
  падає, і проєкт мусить свідомо перегенерувати.

**Прийнято як ціна:**

- Згенерований файл — усе-таки копія: він не отримує змін апстріму автоматично, лише
  дізнається, що відстав. Це навмисно — автоматичне підтягування зробило б пілот
  невідтворюваним посеред вікна вимірювання.
- `generated_at` не бере участі в порівнянні, тому повторний `sync` без змін апстріму
  нічого не переписує: інакше диф кожного проєкту churn-ився б щодня.

**Відкладене:**

- Глобальна зміна дефолту `isolation` в апстрімі **не ухвалюється цим ADR**. Вона
  ухвалюється на даних пілота: `implementation-agent` звужений у english-grammar,
  `test-writer` навмисно лишений на дефолті як контрольна група в тому ж проєкті й
  тому ж вікні. Якщо виправиться тільки перший — причина справді в ізоляції; якщо
  обидва — ефект дали компенсації промпту (фаза 3), і глобальне вимкнення не потрібне.
