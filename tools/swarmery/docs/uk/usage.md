# Використання — живі квоти підписки в хідері

Чип `◔` у хідері та модальне вікно «Використання» за ним відповідають на одне запитання: **скільки
квоти моєї підписки Claude лишилося і чи не спалюю я її швидше, ніж біжить годинник?** Числа —
це *справжнє* показання: демон запитує в Anthropic власні вікна квоти оператора, використовуючи
власний логін `claude` оператора, — той самий виклик, який робить `claude /usage`. Вони не
виводяться з проіндексованих транскриптів.

> [!IMPORTANT]
> Два правила діють усюди на цій поверхні: **жодне число ніколи не вигадується** і **жоден
> збій ніколи не минає мовчки**. Кожний режим відмови — відмова від функції, відсутній логін,
> відхилений токен, обмеження частоти, зміна ендпоінта — деградує до видимої картки помилки
> для відповідного провайдера. Відсутня картка була б брехнею; хибне число — ще гірше.

---

## 1. Джерела даних

### Які акаунти з’являються

Список акаунтів **не** виявляється з облікових даних — це той самий список, з якого конвеєр
індексації читає транскрипти. Кожний налаштований корінь проєктів (`SWARMERY_PROJECTS_ROOTS`;
`auto` один раз під час старту демона розгортає глоб `~/.claude*/projects`) — це один акаунт:
батьківська тека кореня є текою конфігурації цього акаунта, а ім’я акаунта виводиться з імені
цієї теки — `~/.claude` → `default`, `~/.claude-work` → `work`. Це той самий ключ, яким
проштамповано рядки сесій, тож картка використання і бейдж сесії завжди сходяться в тому, що
означає акаунт.

Практичні наслідки: новий акаунт з’являється після того, як у його теці конфігурації виникла
тека `projects/` (тобто під ним відпрацювала хоча б одна сесія) **і** демон перезапустився —
глоб `auto` обчислюється один раз на старті. Без жодного налаштованого кореня список складається
рівно з одного акаунта `default`, що відповідає поведінці до появи кількох акаунтів. Ендпоінти
під’єднання (розділ 6) приймають лише акаунти з цього списку — через API не можна зберегти
облікові дані під довільним ім’ям.

### Розв’язання облікових даних для кожного акаунта

Кожний акаунт спершу перевіряє **власне сховище swarmery** — `~/.swarmery/credentials/<account>.json`,
записане потоком *Під’єднати акаунт* у дашборді (тека `0700`, файл `0600`, атомарні записи).
Знахідка у сховищі перемагає беззастережно. Цей файл належить лише swarmery: *Перепід’єднати*
замінює його тим самим атомарним записом, *Від’єднати* видаляє, а картка, яку він живить,
позначається в корисному навантаженні як `connectedVia: "swarmery"` — саме так модальне вікно
знає, на яких картках мають бути ці дві дії.

Для акаунта **не за замовчуванням** під’єднання додатково виконує **одноразову передачу
облікових даних**: збережені облікові дані один раз копіюються в `<configDir>/.credentials.json`
(режим `0600`, та сама форма `claudeAiOauth`), щоб CLI `claude` міг узяти їх як логін цього
акаунта. Передача відбувається за принципом **write-once** — swarmery ніколи не оновлює цей файл,
ніколи не перезаписує наявний і ніколи не торкається `~/.claude` акаунта за замовчуванням;
ротація токена й далі відбувається лише у власному сховищі swarmery. Докази й обґрунтування:
`docs/claude-cli-credential-behaviour.md` (виміряно 2026-08-12).

Після сховища розв’язання залежить від акаунта:

- **Іменований акаунт** (не за замовчуванням) читає `<configDir>/.credentials.json`
  **виключно** — без запасних варіантів у домашній теці, без `CLAUDE_CONFIG_DIR`, без keychain.
  Будь-який запасний варіант тут розв’язав би облікові дані акаунта *за замовчуванням* і
  опублікував би його квоту під ім’ям іншого акаунта; промах замість цього рендерить картку
  `Connect` для цього акаунта.
- **Акаунт за замовчуванням** переходить до успадкованого ланцюжка. **Перемагає перша
  знахідка**, а кожний окремий промах мовчазний (нечитабельне або відсутнє джерело — просто
  наступний кандидат):

| # | Джерело | Примітки |
|---|---|---|
| 1 | `$CLAUDE_CONFIG_DIR/.credentials.json` | лише коли задано `CLAUDE_CONFIG_DIR`; дзеркалить власне перевизначення CLI |
| 2 | `~/.claude/.credentials.json` | звичайне розташування |
| 3 | `~/.config/claude/.credentials.json` | альтернативне розташування CLI |
| 4 | елемент macOS Keychain `Claude Code-credentials` | лише macOS, через `security find-generic-password`; обмежено 5 с, щоб запит keychain не міг заклинити опитування дашборду |

Приймаються обидві форми облікових даних, які коли-небудь поставляв CLI: облікові дані,
вкладені під `claudeAiOauth`, і голий об’єкт облікових даних у корені файлу. Усе, що не має
`accessToken`, вважається *відсутнім*, а не помилкою. Вичерпання джерел акаунта дає його картку
`not connected`, а не 500.

Сама квота береться з `GET https://api.anthropic.com/api/oauth/usage` (bearer +
`anthropic-beta: oauth-2025-04-20`); оновлення токена, коли потрібно, іде на
`https://platform.claude.com/v1/oauth/token`. Облікові дані мають нести скоуп `user:profile` —
але наперед відхиляється лише *заповнений* список скоупів, у якому його немає, бо CLI не
завжди зберігає список скоупів, і відхилення таких випадків відрізало б справді залогінених
операторів.

**Необов’язкова друга картка.** Коли задано `SWARMERY_USAGE_LIMITS`, додається провайдер
`Telemetry estimate`, обчислений із власних проіндексованих лічильників токенів демона, а не з
даних Anthropic. Він з’являється **лише** тоді, коли задано цю змінну — немає змінної, немає
картки. Він підписаний явно, щоб його ніколи не можна було сплутати з живим показанням:

```bash
SWARMERY_USAGE_LIMITS='{"session5h":{"label":"5-hour session","tokens":50000000,"windowHours":5},
                        "weekly":{"label":"Weekly","tokens":300000000,"windowHours":168}}'
```

`used` рахує проіндексовані токени входу+виходу в ковзному вікні по **всіх** проєктах,
включно з архівованими — квота списується незалежно від того, чи ви архівували проєкт. Вікно
прив’язане до фіксованої сітки епох, тож зворотний відлік «скидання через» стабільний між
опитуваннями; це оцінка графіка скидання, а не справжній графік Anthropic. Некоректне значення
— єдина помилка конфігурації, що відповідає HTTP 500 замість деградації.

## 2. Що показує модальне вікно

- **Чип** — `◔ 42%` для сесійного вікна першого здорового провайдера (із відкатом до першого
  вікна цього провайдера, тож навантаження лише з тижневим вікном усе одно щось каже).
  Червоний понад 90 % використання **або** щоразу, коли темп `ahead`; бурштиновий понад 70 %.
  Підказка містить підпис, відсоток, текст скидання і повідомлення про темп. Сірий `◔ usage`
  означає, що нічого ще не завантажилося; `◔ usage` звичайного тону означає, що ви не залогінені.
- **Одна картка на провайдера** — гліф, назва, чип плану (`Max` / `Pro` / `Team`, виведений із
  `subscriptionType` облікових даних, інакше зі збігу ключового слова `rateLimitTier`, ніколи
  не вгадується) і бейдж статусу: нічого для `ok`, `error` або `not connected` для `no-auth`.
  Провайдер зі збоєм рендериться як ця картка з червоним блоком помилки й без рядків — він
  ніколи не валить модальне вікно.
- **Один рядок на вікно** — підпис, відсоток, індикатор прогресу, забарвлений за *фактичним*
  витрачанням, тонка позначка, що показує, скільки **часу** вікна минуло, зворотний відсоток,
  `resets in …`, чип абсолютного часу скидання і рядок темпу.
- **Режим відображення** — перемикач `Used` / `Remaining`. Колір індикатора завжди відстежує
  реальне використання: у режимі `Remaining` майже вичерпане вікно й далі червоне, а не
  «майже порожнє, отже зелене».
- **Під’єднати / Перепід’єднати / Від’єднати** — картка без читабельних облікових даних
  пропонує `Connect account`: swarmery карбує PKCE-авторизацію, ви схвалюєте її в браузері і
  вставляєте назад `code#state`, який показує сторінка зворотного виклику. Картка, чиї
  *збережені у swarmery* облікові дані зіпсувалися (оновлення відхилено, токен відхилено, скоуп
  відсутній), пропонує той самий потік як `Reconnect` — і навмисно **не** показує жодної
  команди `claude`, бо CLI не пише у сховище swarmery, і її запуск нічого не змінив би.
  `disconnect` у підвалі картки з’являється лише на картках, позначених `connectedVia: "swarmery"`,
  і просить вбудованого підтвердження, перш ніж щось видалити; що саме видаляється — див.
  розділ 4.
- **Приховування окремого вікна** — перемикач `◉` згортає вікно, яке вас не цікавить;
  `show hidden (N)` повертає їх. Обидва налаштування зберігаються в `localStorage` під ключем
  `swarmery.usage.prefs`, з ключем за **назвою** провайдера плюс серверним `key` вікна, і вони
  **глобальні** — квота є фактом рівня акаунта, тож приховане вікно лишається прихованим у всіх
  проєктах. Ключі, які демон перестає повідомляти, вичищаються автоматично.
- **Підвал** — `Last updated: hh:mm:ss`, явна кнопка `refresh` і `close`. Після невдалого
  оновлення останні хороші картки лишаються на екрані з `· refresh failed` у підвалі; модальне
  вікно переходить у жорстку помилку лише тоді, коли *нічого* ще ніколи не завантажувалося.

### Вікна

| Вікно | Джерело в корисному навантаженні | Підпис |
|---|---|---|
| 5-годинна сесія | `five_hour`, інакше `session` | `Session (5h)` |
| Тижневе | `seven_day` | `Weekly` |
| Тижневе, за моделлю | `seven_day_sonnet` / `seven_day_opus` | `Weekly (Sonnet)` / `Weekly (Opus)` |
| Тижневе, за моделлю (поточна форма) | загальний обхід `limits[]` — записи з `group: "weekly"` (або `kind`, що починається з `weekly`), числовим `percent` і `scope.model.display_name` | `Weekly (<model>)` |

Обхід `limits[]` — причина, чому нові моделі з’являються без зміни коду: спостерігалося, що
Anthropic постачає там тижневе використання за моделями, обнуляючи успадковані ключі
`seven_day_opus` / `seven_day_sonnet`. Модель, уже видана іменованим ключем, не дублюється.
Запис без назви моделі або без придатного відсотка пропускається — один відсутній рядок, а не
зламана відповідь.

`key` вікон — це слаги підпису (`Session (5h)` → `session-5h`, `Weekly (Fable)` →
`weekly-fable`), стабільні між оновленнями, і саме це дає налаштуванням приховування пережити
перезавантаження. Ключі картки-оцінки — це натомість ключі вашого об’єкта
`SWARMERY_USAGE_LIMITS`, тож обидві картки можуть законно мати однакове ім’я ключа;
налаштування рознесені за просторами імен провайдерів, тож приховування одного ніколи не
приховує інше.

Відсотки обрізаються до 0–100. Коли сесійне вікно надходить без придатного моменту скидання,
припускається повне 5-годинне вікно, щоб рядок усе ж рендерив зворотний відлік; цей запасний
варіант навмисно **не** застосовується до тижневих вікон, бо вигадане тижневе скидання — це
брехня, яку оператор не зможе помітити.

## 3. Контракт темпу — прочитайте, перш ніж довіряти кольорам

Темп порівнює витрачену квоту з часом вікна, що минув, у **відсоткових пунктах**:

```
delta = percentUsed − percentElapsed
```

з **мертвою зоною ±5 відсоткових пунктів**. Словник з першого разу читається навпаки, і це
найчастіше хибно прочитувана річ на цій поверхні:

| Дельта | Статус | Значення | Колір |
|---|---|---|---|
| `> +5` п. | **`ahead`** | квота спалюється **ШВИДШЕ**, ніж минає час — **понад темп, стан-попередження** | червоний |
| `−5 … +5` п. | `on-track` | у темпі з часом, що минув | зелений |
| `< −5` п. | `behind` | спалюється **повільніше**, ніж минає час — **нижче темпу, хороший стан** | зелений |

Отже, `ahead` — це погано, а `behind` — добре. Це не баг, і обмін кольорів інвертував би зміст.

Розібрані приклади:

| Використано | Минуло | Дельта | Статус | Повідомлення |
|---|---|---|---|---|
| 28% | 22% | +6 | `ahead` | `6% over pace` |
| 19% | 25% | −6 | `behind` | `6% under pace` |
| 28% | 30% | −2 | `on-track` | `On pace with time elapsed` |
| 60% | 20% | +40 | `ahead` | `40% over pace` |

Темп **відсутній** (немає об’єкта `pace`, немає позначки, немає рядка темпу), коли вікно не
має сигналу часу вперед — невідомий момент скидання або вікно, що вже минуло своє скидання.
Він обчислюється один раз на сервері, тож обидві картки й обидва споживачі поділяють одне
визначення; ніщо у фронтенді не виводить його повторно.

## 4. Позиція щодо безпеки

Bearer-токен — єдина причина, чому цій поверхні потрібен розділ про безпеку. Контракт:

- **Він іде лише до Anthropic** — виставляється як заголовок `Authorization` у запиті
  використання і ні в чому іншому. Це той самий виклик, який робить CLI `claude`.
- **Ніколи не зберігається.** Жодної таблиці SQLite, жодної міграції, жодного файлу кешу. Про
  використання нічого не зберігається; кожне читання живе або віддається з 30-секундного кешу
  *обчисленої відповіді* в пам’яті, який не містить матеріалу облікових даних.
- **Ніколи не логується.** Власне рядкове подання типу облікових даних рендериться як
  `usage.Creds{redacted}`, тож випадковий `%v` чи `%+v` будь-де в дереві друкує константу, а не
  токен.
- **Ніколи не віддається.** Жодна HTTP-відповідь демона не несе матеріалу облікових даних.
  Тіла помилок від upstream очищаються від bearer-матеріалу й `sk-…` *до* обрізання — тож
  токен не може вижити як частковий суфікс — і обмежуються 120 символами.
- **Оновлені токени ніколи не потрапляють у джерело CLI.** Оновлення (одна спроба на 401/403 і
  наперед, коли збережений токен перебуває у своєму 60-секундному пільговому періоді перед
  закінченням) зберігається лише у **власному** сховищі swarmery для облікових даних, що
  належать сховищу, і лишається тільки в пам’яті для облікових даних, прочитаних із джерела CLI
  — **ніколи не записується назад** у `<configDir>/.credentials.json` чи keychain. Єдиний
  виняток із правила «демон не пише файли CLI» — описана вище **одноразова передача під час
  під’єднання**, яка записує свіжий `<configDir>/.credentials.json` щонайбільше один раз і
  ніколи його потім не оновлює.
- **`SWARMERY_USAGE_OAUTH=0` — справжній вимикач.** Він обриває роботу, перш ніж буде зачеплене
  будь-яке джерело — жодного читання файлу, жодного виклику `security`, жодного запиту keychain —
  а картка повідомляє `usage OAuth disabled (SWARMERY_USAGE_OAUTH=0)`. Він накриває й половину
  на запис: під’єднання, перепід’єднання і від’єднання відповідають `409`, доки його задано.
- **Від’єднання видаляє один файл — наш.** `disconnect` на картці видаляє
  `~/.swarmery/credentials/<account>.json` і більше нічого. Він ніколи не торкається
  `<configDir>/.credentials.json` чи елемента macOS keychain — після передачі (або запису
  логіном CLI) вони належать CLI `claude`, а кнопка дашборду, здатна обірвати ваш логін у
  терміналі, була б пасткою. Акаунт просто відкочується по решті ланцюжка розв’язання, зазвичай
  до своєї картки `Connect`. Операція ідемпотентна: від’єднання вже від’єднаного акаунта
  успішне. Оновлений bearer у пам’яті скидається разом із файлом, тож з’єднання не може пережити
  його до наступного перезапуску демона.
- **Від’єднання *не* відкликає нічого в Anthropic.** У цьому потоці немає кроку відкликання:
  токени лишаються чинними на боці upstream, доки самі не закінчаться. Закінчується
  використання їх *цим демоном*. Щоб відкликати саму авторизацію, зробіть це зі свого акаунта
  на claude.ai.

## 5. Застереження про стабільність

`/api/oauth/usage` **не задокументовано**. Він може змінити форму, почати відмовляти цьому
клієнту або зникнути — без попередження і без періоду застарівання. Цей ризик прийнято і
стримано, а не приховано:

- запит ніколи не повертає помилку — кожний результат кодується як `status` + `error`
  провайдера, тож один зламаний провайдер ніколи не зламає ендпоінт чи дашборд;
- кожне читання поля толерантне (кілька прийнятних написань ключа на поле; моменти скидання
  приймаються як RFC3339, unix-секунди або unix-мілісекунди, числом чи числовим рядком), тож
  перейменування поля коштує одного рядка, а не відповіді;
- тіло, що не є коректним JSON, дає `Claude usage response was not valid JSON` — картку помилки,
  а не крах і не нуль, відрендерений як справжнє число.

Якщо ендпоінт зникне, чесний результат — постійна картка помилки. Виправляйте парсер за
захопленим навантаженням; не замазуйте проблему обчисленою здогадкою.

### Що означають картки помилок

| Текст картки | Статус | Що робити |
|---|---|---|
| `usage OAuth disabled (SWARMERY_USAGE_OAUTH=0)` | not connected | нічого — ви самі відмовилися |
| ``No Claude credentials — run `claude` to log in`` | not connected | залогіньтеся через CLI на цій машині |
| ``Claude token missing user:profile scope — re-run `claude` login`` | not connected | повторіть логін у CLI |
| ``Claude token expired and no refresh token — run `claude` to re-login`` | error | повторіть логін у CLI |
| ``Claude token refresh failed — run `claude` to re-login`` | error | повторіть логін у CLI |
| ``Claude auth rejected — run `claude` to re-login`` | error | токен відхилено навіть після одного оновлення |
| `Claude usage rate-limited (HTTP 429) — retry later` | error | три спроби витрачено з дотриманням `Retry-After`; зачекайте |
| `Claude usage request failed: …` | error | мережа/DNS/TLS; повідомлення очищене від секретів |
| `HTTP <code>: <snippet>` | error | upstream відповів щось несподіване — ймовірно, змінився ендпоінт |
| `Claude usage response was not valid JSON` | error | форма навантаження змінилася; захопіть його і виправте парсер |

Колонка з ліками припускає логін через CLI. На картці з позначкою `connectedVia: "swarmery"`
кожний рядок вище, що стосується облікових даних, означає *натомість перепід’єднайтеся з
картки* — підказка там не містить команди, бо `claude` пише у сховище, з якого ці облікові дані
ніколи не бралися.

## 6. Довідник API

| Ендпоінт | Призначення |
|---|---|
| `GET /api/usage` | усі картки провайдерів; віддається з 30-секундного кешу на весь процес |
| `GET /api/usage?fresh=1` | обминути **читання** кешу і запитати наживо (результат усе одно наповнює кеш) |
| `POST /api/usage/accounts/{account}/login/start` | почати авторизацію; відповідає `{authorizeUrl}` і більше нічим — PKCE-верифікатор і CSRF-стан лишаються в демоні |
| `POST /api/usage/accounts/{account}/login/complete` | завершити її з `{"code":"<code>#<state>"}`; зберігає облікові дані і скидає кеш використання |
| `DELETE /api/usage/accounts/{account}/login` | від’єднати: видаляє власні облікові дані swarmery для акаунта (розділ 4), скидає кеш використання, `{ok:true}` |

Три ендпоінти на запис мають однакові запобіжники: локальне походження, `{account}`, який
демон справді опитує (`404` інакше — включно з DELETE, який ідемпотентний для *відомого*
акаунта, але ніколи для невідомого), і `409`, доки задано `SWARMERY_USAGE_OAUTH=0`.

Без скоупу — квота є фактом рівня акаунта, тож параметра `project` немає. Весь живий запит
обмежено 20 секундами (окремі HTTP-виклики — 15 с), із щонайбільше 3 спробами на 429 з
дотриманням числового `Retry-After`, а інакше з відступом 1 с → 2 с → 4 с.

Збої провайдерів відповідають **HTTP 200** із карткою помилки. Єдині не-200 — `500` за

## 7. Частоти опитування

Один опитувач обслуговує і чип, і модальне вікно, бо кожний промах кешу коштує справжнього
виклику до upstream, а два таймери на один ендпоінт подвоїли б цю частоту без жодної додаткової
інформації.

| Коли | Частота |
|---|---|
| чип змонтовано, модальне вікно закрите | **120 с** |
| модальне вікно відкрите | **30 с** (збігається з TTL власного кешу демона) |
| вкладка браузера прихована | **повна пауза** — таймера не існує |
| вкладка знову стає видимою | **один** запит навздогін, і лише якщо знімок уже пережив чинну частоту; швидкий перехід на іншу вкладку й назад нічого не коштує |
| модальне вікно відкрито | **один** запит, і лише якщо знімок уже старший за 5 с — тож відкриття модального вікна двічі поспіль коштує одного виклику, а не двох |
| завантаження сторінки | один запит під час монтування |
| кнопка `refresh` | негайно, і це **єдине**, що надсилає `?fresh=1` |

Автоматичні опитування ніколи не надсилають `?fresh=1` — їх поглинає 30-секундний кеш демона,
тож стала частота до upstream — щонайбільше один виклик на 30 секунд, скільки б вкладок не
було відкрито. Відкриття модального вікна і змінює спільну частоту (з підрахунком посилань, тож
подвійне монтування не може залишити її застряглою на швидкому режимі), *і* виконує описаний
вище запит, обумовлений застарілістю: зміна затримки `setInterval` не змушує його спрацювати,
тож без цього запиту панель відкривалася б із тим, що останнім витягла повільна 120-секундна
частота. Закриття модального вікна ніколи не робить запитів. Окремо модальне вікно щораз на 30 с
тікає суто показовим годинником, щоб `resets in …` лишався живим між опитуваннями.

## 8. Важелі оператора

| Змінна | Ефект |
|---|---|
| `SWARMERY_USAGE_OAUTH=0` | повністю вимикає читання облікових даних — жодного файлу, жодного keychain, жодного виклику до upstream. Картка про це повідомляє. |
| `CLAUDE_CONFIG_DIR` | тека першого джерела облікових даних, попереду `~/.claude` |
| `SWARMERY_USAGE_LIMITS` | JSON-конфігурація квоти; саме її присутність породжує картку `Telemetry estimate` |

Перевірка вручну:

```bash
curl -s localhost:7777/api/usage | jq                    # з кешу (не старше 30 с)
curl -s 'localhost:7777/api/usage?fresh=1' | jq          # живий виклик до upstream
SWARMERY_USAGE_OAUTH=0 ./swarmery serve                  # перевірити шлях відмови від функції
```

## 9. Чому `/usage` у моєму терміналі показує інший акаунт

Прив’язка проєкт → акаунт керує тим, що swarmery **відправляє**: запусками, стартованими з
дашборду, і вбудованим терміналом дашборду. `claude`, який ви запускаєте вручну у власній
оболонці, нічого про неї не знає — без `CLAUDE_CONFIG_DIR` у цій оболонці CLI читає
`~/.claude`, тобто акаунт машини **за замовчуванням**. Тож `/usage` у відкритому вручну
терміналі може чесно не збігатися з акаунтом, під яким, за словами дашборду, працює цей проєкт;
ніхто не бреше — вони відповідають на різні запитання.

Щоб запустити стартований вручну CLI під акаунтом проєкту, з кореня проєкту:

```bash
swarmery account which            # під яким акаунтом працює цей проєкт і чому
swarmery account exec -- claude   # виконати одну команду під цим акаунтом
eval "$(swarmery account env)"    # або експортувати CLAUDE_CONFIG_DIR у цю оболонку
```

`which|use|clear|env|exec` ніколи не звертаються до демона, тож працюють і коли swarmery
зупинено. Якщо `which` повідомляє `source: default`, хоча файл називає акаунт, перевірте
попередження на stderr. `settings.local.json`, який відстежує git, ігнорується навмисно (див.
*Прив’язка акаунта* в документі про поняття). Зніміть його з відстеження через `git rm --cached`
і додайте в gitignore. `/account setup-shell` із пакета акаунтів встановлює обгортку оболонки,
яка застосовує прив’язку автоматично для кожної теки.
