# Ретро — ретроспективи агентної системи й цикл покращення

Цикл ретро — сторінка **Здоров’я** дашборду (`/health`; стара адреса `/retro`
переадресовує туди) — відповідає на одне питання: **як працює агентна система і що
нам варто змінити?** Він перетворює телеметрію, яку демон
і так збирає, — плюс артефакти, які агентний робочий процес пише в робочий простір, — на
табелі здоров’я кожного агента, дошку тертя, стрічку уроків і конкретні, суто евристичні
рекомендації з покращення з відстежуваним життєвим циклом
(`proposed → accepted → adopted → verified`).

Жодна LLM не бере участі ні в числах, ні в рекомендаціях: кожне з них — детерміноване згортання
над SQLite. Моделі викликаються лише явними діями **Покращити** (переписування агента
або аналіз усієї системи) і щоденним суддею траєкторій — див. документ «Поняття».

## 1. Джерела даних

Ретро зводить три шари, які раніше жили в окремих світах:

| Шар | Джерело | Хто інжестить | Куди лягає |
|---|---|---|---|
| **Телеметрія сесій** | Транскрипти Claude Code (`~/.claude/projects/**.jsonl`) | `internal/ingest` (стеження за хвостом) | `sessions`, `turns` (атрибуція по агентах), `events` (виклики інструментів, помилки, старт/стоп субагентів), `file_changes` |
| **Артефакти робочого простору** | `$AGENT_WORKSPACE_ROOT/<project>/workspace/{working,archive}/YYYY/MM/DD/<slug>/` | `internal/wsingest` (пересканування кожні 60 с, з хеш-гейтом SHA-256) | `task_retros`, `retro_lessons`, `retro_improvements`, `task_loops`, `task_delegations` |
| **Результати евалів** | promptfoo `results.json` із набору `evals/` | `swarmery evals-import --agent <name> <file>` (ручний CLI) | `eval_suites`, `eval_cases`, `eval_runs`, `eval_results` |

Для кожної задачі розбираються три артефакти робочого простору (толерантний контракт — некоректний
вхід дає попередження й пропуск, а не збій сканування):

- `phases/09-retrospective.md` — рядок метрик Duration, записи `### Lesson N:`
  (разом із їхніми рядками `**Action**:`) і таблиця Process Improvements.
- `ORCHESTRATION.md` — секції журналу повторних відправок `## Loop {N}`.
- `logs/agents.md` — реєстр делегувань (заголовок українською або англійською). Приймаються дві
  розкладки рядка: застаріла 4-коміркова `agent | phase | verdict | artifact`
  і оцінювальна 7-коміркова `agent | phase | verdict | loops | quality | mistakes | artifact`
  (tech-lead ≥ core 2.2.0). Артефакт завжди в останній комірці; буквальний `|`
  усередині mistakes склеюється назад. Кількість циклів поза межами (не в 0..99) і якість
  (не в 1..5) деградують до NULL, не відкидаючи рядок.

## 2. Де це живе в дашборді

Вкладки сторінки «Здоров’я» ділять цикл за питаннями; смуга стану зверху тримає один діапазон дат
для всіх них.

| Вкладка | Що містить |
|---|---|
| **Огляд** | Одне речення про флот, агентів, які його рухали, і тертя, яке можна усунути прямо зараз |
| **Агенти** | **Смуга здоров’я** — вартість оркестратора (`main`), загальна кількість запусків субагентів, загальна кількість помилок, кожне зі стрілкою «проти попереднього вікна» — і **табелі агентів**: по картці на агента, відсортовані за запусками: запуски (+дельта до попереднього), частка помилок, частка успіху, вартість, тривалість p95, чип повторних делегувань, чип евалів |
| **Тертя** | **Дошка тертя** — інструменти, яким найчастіше відмовляли, з кнопкою `+ rule` в один клік (створює правило автопогодження), повторювані групи помилок (розгортаються, зі зразками сесій), статистика чекання погоджень |
| **Оцінки** | **Точність оцінок** — для кожної задачі: оцінені проти фактичних годин, бейдж відхилення (зелений ≤ ±20 %, жовтий ≤ ±50 %, червоний далі), кількість циклів, розклад вердиктів делегувань — і **стрічка уроків**: кожен розібраний урок з усіх задач, найновіші спершу, з фільтром на клієнті й поданням **Групувати за уроком** (§7). Чип `action` — головне: це інструкція, яку можна використати повторно |
| **Радник** | **Рекомендації** — вивід радника (§4–5) — і **пропозиції** змін агентів/скілів, що чекають на рішення |
| **Вартість і токени** | Вартість, токени, запуски й кеш у часі |

Пресети діапазону (7/14/30/90 д) і область проєкту (перемикач проєктів у сайдбарі)
діють на все. Відкриті рекомендації й пропозиції потрапляють також у **Вхідні**
(їхні вкладки *радник* і *пропозиції*) — саме там їх рахує єдиний бейдж сайдбара.

## 3. Визначення метрик

Зерно агрегації навмисно повторює «Здоров’я → Вартість і токени» та радника, тож число,
на яке посилається рекомендація, збігається з тим, що показують сторінки.

| Метрика | Визначення |
|---|---|
| **runs** | Події `subagent_start`, згруповані за `payload.subagent_type` (згорнуто: `core:x` → `x`; `NULL` → `main`, показується окремо). |
| **errors** | Сира кількість подій-помилок, приписаних агенту через `parent_event_id → subagent_start` (`turn_id` подій навмисно НЕ використовується — інжест обнуляє його для подій бічного ланцюжка). Дзеркальні рядки-помилки `subagent_start` виключено, щоб не рахувати невдалі запуски двічі. |
| **error_rate** | **Частка невдалих запусків**: окремі запуски з ≥ 1 помилкою ÷ запуски, з дедуплікацією за id `subagent_start` запуску. Обрізається до ≤ 1 (запуск, що перетинає початок вікна, може додати невдалий запуск, не додавши запуск до лічильника). Це *не* помилки-на-запуск — запуск із п’ятьма помилками інструментів рахується один раз. |
| **success_rate** | Ручні результати сесій: `success / (success + fail)` над сесіями з результатом, що містять ходи агента. Null, доки ви не оціните сесії (вибір ✓/✗/⊘ на сесії). |
| **cost / tokens** | Сума з `turns`, де `turns.agent_name` згортається до агента (точна атрибуція по агентах із ходів бічного ланцюжка). |
| **re-dispatch rate** | Частка рядків реєстру делегувань агента, чий вердикт відповідає двомовній граматиці `re-dispatch / fail / reject / повтор / відхил / провал / фейл` (комірки понад 40 рун вважаються прозою, не вердиктами). Застереження: для агентів-*рев’юерів* вердикт «повторне делегування» зазвичай означає, що рев’юер зробив свою роботу. |
| **evals chip** | `passed/total` з останнього імпортованого запуску евалів для агента. |
| **approx flag** | Ставиться, коли діапазон (або його вікно порівняння) перекриває обрізані дні, що існують лише як денні згортки — числа там чесні, але неповні. |

## 4. Радник — правила R1–R6 (плюс R10, R11, R13, R14)

> [!NOTE]
> Радник реєструє більше правил, ніж описано в цьому розділі. Авторитетний перелік — `advisor.Run` у
> `internal/advisor/advisor.go`; правила, описані нижче, —
> це первісні шість, плюс R10 (бюджет індексу автопам’яті), R11 (повторюваний
> урок), R13 (автопам’ять, що називає злиті PR відкритими) і R14 (повторювана правка
> оператора), кожне зі своїм підрозділом після таблиці.

`internal/advisor` запускається на старті демона, за тікером кожні 24 год і на вимогу
(`Аналізувати` → `POST /api/retro/advise`). Кожне правило оцінює ковзне
**14-денне** вікно; повторні запуски оновлюють докази відкритих рекомендацій на місці (без
дублікатів). Кожна картка несе JSON `evidence` з вікном, лічильниками й зразками
id сесій.

| Правило | Ціль | Спрацьовує, коли | Пропонована дія |
|---|---|---|---|
| **R1** тертя інструмента | tool | відмовлено ≥ 5× і жодне увімкнене правило погодження не покриває інструмент | додати правило автопогодження (кнопка `+ rule` на дошці тертя робить це в один клік) |
| **R2** частка помилок агента | agent | запусків ≥ 10, подій-помилок ≥ 3 і частка невдалих запусків > 2× медіани флоту (серед агентів із ≥ 10 запусками) | переглянути промпт агента; картка наводить його найчастішу групу помилок |
| **R3** повторювана помилка | error group | та сама нормалізована помилка в ≥ 3 різні дні | виправити першопричину (правило в промпті, хук, allowlist, інфраструктура) |
| **R4** повторне делегування | agent | ≥ 3 рядки реєстру і частка повторних делегувань > 25 % | загострити бриф / критерії приймання агента; розглянути кейс для евалів |
| **R5** застаріле покращення | process | високопріоритетний рядок Process Improvements досі відкритий через 14 д після інжесту його ретро | зробити його, потім позначити рядок `done` у документі ретро |
| **R6** регресія кешу | config | частка влучань кешу впала > 10 п. п. проти попереднього вікна | перевірити зміни в структурі промптів/сесій |
| **R10** індекс автопам’яті | memory | `MEMORY.md` проєкту > 6 КіБ **або** > 50 % його ≥ 10 рядків індексу закриті | запустити `swarmery memory consolidate` (див. нижче) |
| **R13** застарілий факт у пам’яті | memory | рядок автопам’яті називає PR і каже, що він відкритий, а git-історія проєкту вже містить його злиття | виправити рядок руками або на «Знання → Memory»; `swarmery memory lint` перелічує їх (див. нижче) |
| **R11** повторюваний урок | skill | одна ідентичність уроку (`norm_title`) трапляється в ≥ 3 **різних** задачах у вікні | перенести урок у той `SKILL.md`, який наступний запуск справді читає |
| **R14** повторювана правка оператора | skill | одну ідентичність правки (`norm_key`) зроблено ≥ 2 рази на ≥ 2 **різних** посиланнях у вікні (урок переписано/прибрано/списано руками, вердикт сортування скасовано, ревізію плану відхилено, відповідь класифікатора спростовано) | вкласти правку в процедуру, яка породила помилку, щоб нікому більше не доводилося робити її руками |

### R10 — бюджет індексу автопам’яті

`<claude-dir>/projects/<slug>/memory/MEMORY.md` завантажується в **кожну** розмову в
проєкті, тож його байти перечитуються на кожному ходу вічно, і кожен рядок про завершену роботу —
це оренда, сплачена ні за що. R10 вимірює це детерміновано й без LLM: на кожному проході він читає
індекс з диска (той самий корінь автопам’яті, що й «Знання → Memory»), розбирає його
рядки `- [Title](file.md) — hook` і класифікує кожен хук як **закритий**, коли той містить
маркер закриття (`DONE|MERGED|CLOSED|SHIPPED|RESOLVED|LIVE`) і **жодного** маркера відкритості
(`OPEN`, `open:`, `tail =`, `impl open`, `awaits`). Рядок з обома — це відкритий хвіст і
рахується як живий: `MERGED … OPEN: flip the guard` лишається, `FULLY CLOSED …; no open tail` закривається.

Два незалежні тригери, бо дві форми збою різні: індекс може бути понад бюджет,
залишаючись цілком живим (забагато тем), і може бути малим, але переважно мертвим (довгий хвіст рядків
DONE). `detail` знахідки починається з чисел — `index 8.1 KB, 28/53 lines closed
(53%)` — а її базова метрика — `memory_index_closed_share` (менше — краще).

Як і R7/R8/R9, воно **самоперевірне**: на кожному проході переоглядає світ, тож консолідований
індекс просто перестає спрацьовувати, і рядок автоматично стає `resolved`. `target_kind` — `memory`
(міграція `0071`), сигналу впровадження в нього немає, і `verify()` ніколи його не вибирає — це
сповіщення, а не виміряне покращення.

Діяти — це `swarmery memory consolidate --project <path> [--dry-run]` або панель
**Консолідувати індекс** на вкладці «Знання → Memory» проєкту (`POST /api/memory/consolidate`).
Консолідація переносить файл теми закритого запису в `memory/closed/`, штампує його
`closed_at` + `status: closed`, переносить його рядок індексу в `memory/closed/INDEX.md` і вилучає
його з `MEMORY.md`. Перенесення **файлу** — несуча половина: файл, залишений у `memory/`, і далі
кандидат на пригадування навіть без рядка в індексі. Нічого не видаляється, кожен зачеплений файл
спершу резервується в одну теку з міткою часу, а `--dry-run` (типово для API) не пише взагалі
нічого. Два записи завжди притримуються: один з відкритим хвостом і один, на чий файл **відкрита**
пам’ять ще посилається через `[[link]]` — закрити такий означало б обірвати живу залежність.
Тут немає ні LLM-злиття, ні пошуку дублікатів поза цими точними маркерами.

### R13 — автопам’ять, що називає злиті PR відкритими

R10 вимірює **розмір** індексу; R13 вимірює його **правдивість** — для того єдиного класу фактів, який
дешево перевірити офлайн. Нотатка автопам’яті пишеться один раз і далі довіряється вічно — `PR #366 UNMERGED
(needs a review approval)` лишався в `MEMORY.md` цього репозиторію тижнями після злиття, і
кожна наступна сесія планувала навколо нього. Ніщо не перечитувало цей факт проти світу.

`internal/memlint` перечитує — детерміновано, без LLM, мережі чи `gh`: він читає кожен
`*.md` безпосередньо під коренем автопам’яті проєкту (той самий резолвер `memconsolidate.AutoMemoryDirIn`,
що спільний для R10, сторінки Memory і CLI; у `closed/` не спускається), ріже кожен рядок на
**клаузи** (на `;`, `, `, `. `, тире з пробілами або табличній рисці), і в кожній клаузі, що містить
**маркер відкритості** (`OPEN|open|UNMERGED|needs a review/merge/approval|awaits|pending|not merged`) і
**жодного маркера закриття** (`MERGED|CLOSED|DONE|SHIPPED|RESOLVED`), кожне посилання `#<n>` на початку слова —
це **твердження**, по одному на рядок. Отож `PR #340 … MERGED; #341 open` стверджує лише про #341, `MERGED + deployed
(#260, #261); OPEN: flip the guard` не стверджує нічого, а `issues/12#issuecomment-1` — узагалі не посилання.
Межа — клауза, а не рядок, навмисно: перша, порядкова версія позначила 45 із 46 тверджень
цього репозиторію, майже всі — рядки, де «open» стосувалося чогось іншого. Кожне окреме твердження перевіряється
один раз проти власної історії проєкту командою
`git -C <project> log --all --max-count=1 --fixed-strings --grep="Merge pull request #<n> " --grep="(#<n>)"`
— дві форми, які залишає GitHub: коміт злиття і squash-коміт; кінцевий пробіл і
дужки не дають `#36` збігтися з `#366`. Збіг — це **знахідка** зі sha злиття й датою комітера.
Проєкт без `.git` має твердження, які не може перевірити, а отже не має знахідок; проєкт без
теки пам’яті пропускається.

R13 спрацьовує один раз на кожен неархівований проєкт із ≥ 1 знахідкою. `detail` називає перші три —
`model-lineup.md:12 says PR #366 is open; it merged 2026-09-22 (2151242)` — а докази несуть
`counts{claims, stale}`, кожну знахідку й `index_path`. Базова метрика — `memory_stale_claims`
(менше — краще; 0, щойно рядки виправлено). `target_kind` — `memory`, як у R10, і, як R10, воно
**самоперевірне**: перелінтовує на кожному проході, тож виправлений рядок перестає його запускати, і рядок закривається
сам. Правило ніколи не редагує файл пам’яті — правка належить оператору, руками або через
вкладку «Знання → Memory» проєкту.

Той самий звіт — `swarmery memory lint --project <path> [--json]` (ніколи не відкриває базу даних),
`swarmery memory lint --all` (кожен неархівований проєкт; єдиний шлях, що читає базу даних,
лише для читання й без міграцій) і `GET /api/projects/{id}/memory/lint`. Усі три завершуються чи відповідають
успішно незалежно від того, чи знайшли щось: це звіт, а не гейт.

### R11 — урок, який флот знову й знову перевчає

Урок із ретроспективи за побудовою — це те, що вже пішло не так один раз. Флот
чесно записує його, а потім вчить знову через три задачі, бо урок живе в документі ретро
завершеної задачі, і ніщо не переносить його вперед у процедуру, яку читає наступний запуск.

R11 виявляє саме це. Рядки `retro_lessons` на кожному перескануванні видаляються й вставляються наново (DELETE+reinsert), тож id рядка
ніколи не міг би бути міжзадачною ідентичністю — міграція **0070** додає `retro_lessons.norm_title`,
який пише `wsingest.NormalizeLessonTitle`: нижній регістр, початковий порядковий `Lesson N:` відкинуто,
пунктуацію згорнуто в пробіли, стоп-слова `the a an of to in for and` вилучено, пробіли
стиснуто, 80 рун. Тож `Lesson 3: Sync-Cache Before Build!` і
`sync the cache before the build` — одна ідентичність. Згортання навмисно не хитре — без
стемінгу, без редакційної відстані, без синонімів: згортання, яке вгадує, злило б два різні уроки
під одним заголовком, і ніхто не побачив би, що це сталося. Назва, що згортається в порожнечу, зберігає
`norm_title = ''`, і **кожен** читач пропускає `''` — це маркер «ще не згорнуто», ніколи не
ідентичність. Рядки, записані до 0070, згортаються одноразово при старті демона бекфілом wsingest
(`retro lessons backfilled: N` у журналі); шлях вставки відтоді згортає все.

Правило спрацьовує, коли один `norm_title` з’являється в ≥ 3 **різних задачах** усередині 14-денного вікна.
Різних задачах, ніколи не рядках: одне ретро, що повторює саме себе, — це здублюваний абзац, а не закономірність.
`detail` читається як `"<title>" recurred in N tasks: <slug…>` (перші 5 id, далі `(+K more)`) плюс
найсвіжіший рядок `**Action**:`; базова метрика — `lesson_task_count` (менше — краще).

`target_kind` — **`skill`** (міграція `0072`), а не `process`, як у R5: R5 вказує на рядок покращення
одного ретро й просить людину зробити його, R11 вказує на процедуру, яка мала б нести
урок і ніколи не несла, — і пропозиції скілів у циклі покращення маршрутизуються саме за цим типом, тож він
несучий, а не прикраса. На відміну від R7/R8/R9/R10, R11 **не** самоперевірне: воно читає збережені
рядки в ковзному вікні, тож два тижні без ретроспектив виглядають точно так само, як два тижні,
за які урок нарешті засвоєно, і закривати на цій підставі рядок `accepted` було б гаданням.
Рядок `proposed` усе ж прибирається, коли правило затихає, і пропонується наново, якщо урок повертається.

Те саме згортання стоїть за перемикачем **Групувати за уроком** на «Здоров’я → Оцінки» — див. `?group=1` у §7.

### R14 — правка, яку оператор робить знову й знову

Кожне місце, де людина перевизначає зроблене агентом, уже існувало й уже
працювало: черга рев’ю уроків (редагувати, прибрати, списати), **Скасувати** вердикту сортування,
**Відхилити** ревізії плану, мітка істини класифікатора. Чого жодне з них не робило — то
*не рахувало*. Кожну правку поглинала її власна функція й забувала, тож ту саму помилку
можна було правити руками з десяток разів, і ніщо цього не помічало.

Міграція **0102** додає `operator_corrections` — по рядку на кожне перевизначення, який пише операторський
**ендпоінт** (`internal/api` lessons/triage/revisions/decisions) після того, як його власний запис вдався,
через `internal/corrections.Record`. Рядок несе `source`
(`lesson_edit | lesson_dismiss | lesson_retire | triage_undo | revision_reject | truth_disagree`),
типізований текстовий `ref` (`lesson:12`, `verdict:88`, `revision:5`, `decision:1947` — без зовнішніх ключів на
гарячі таблиці, за 0073), `before`/`after`, операторську `reason` і `norm_key`: причину — або
текст after, коли на поверхні немає поля причини, — згорнуту **тим самим**
`wsingest.NormalizeLessonTitle`, що й у R11, тож дві по-різному сформульовані правки одного й того самого —
одна ідентичність, а `''` — «без ідентичності», і кожен читач його пропускає. Два навмисні мовчання: правка
уроку, що не змінює ні назви, ні настанови (лише глоби областей), рядка не пише, і
мітка істини, що *погоджується* з класифікатором, рядка не пише — мітка не є правкою.
Невдалий запис у реєстр журналюється й ніколи не провалює дію оператора. Реєстр пишеться на
ендпоінті й **ніколи всередині `lessons.Retire`**: автосписання перевіряльника викликає його теж, а
демон, що списує власний урок, — не людина, що його править (це закріплює `internal/lessons`).

R14 спрацьовує, коли один `norm_key` правили ≥ 2 рази на ≥ 2 **різних посиланнях** усередині
14-денного вікна. Різних посиланнях, ніколи не рядках: той самий урок, відредагований двічі, — це оператор, що доводить
думку до кінця, а не закономірність. `detail` читається як `"<sample>" was corrected N times across <ref…> (<sources>)`;
докази несуть `counts{corrections, refs}`, `refs`, `sources`, `norm_key`; базова
метрика — `correction_count` (менше — краще; нуль рядків — це «немає даних», а не нуль).

`target_kind` — **`skill`**, а ціль — `norm_key`, точно як у R11, тож пропозиції скілів у циклі
покращення маршрутизують його без змін, і рекомендація — людський гейт, перш ніж щось буде
переписано. Як і R11, воно **не** самоперевірне: два тижні, за які ніхто нічого не правив,
виглядають так само, як два тижні, за які помилку перестали робити.

`GET /api/corrections?window=14d&limit=200` повертає вікно як `{groups, rows}` — те саме згортання,
що читає R14, для майбутньої сторінки; POST немає, бо правка — це те, що оператор *зробив*.

### Пропозиції скілів — на що перетворюється R11

Прийняття рекомендації R11 спрямовує її в **той самий** конвеєр диффів з людським гейтом, яким користуються
переписування агентів (`internal/improve`), націлений на `SKILL.md` замість визначення агента. Рядок
пропозиції каже, на файл якого типу він націлений: `agent_change_proposals.target_kind` — `agent`
або `skill`, а `target_path` містить відносний до репозиторію `plugins/<pack>/skills/<name>/SKILL.md`
(міграція `0074`). Більше в конвеєрі нічого не змінюється — дифф і далі потребує людського
«Погодити», і йому й далі треба пройти сканер нейтральності, перевірку frontmatter, жорсткий гейт
області шляхів і ліміт ≤120 рядків, перш ніж з’явиться PR.

**Визначення цілі.** `target` рекомендації — це ідентичність уроку (`norm_title`), а не
файл. Файл береться з найсвіжішого рядка `**Action**:` уроку, коли той називає скіл —
буквальний токен `skills/<name>`, — і резолвиться проти `origin/main` репозиторію застосування. Піти не так
можуть дві речі, і обидві закінчуються рядком, який ви бачите, а не мовчанням:

| Рядок Action | Результат |
|---|---|
| називає `skills/<name>`, який постачає якийсь пакет | пропозиція `proposed`, `target_path` задано, дифф згенеровано |
| не називає скілу або називає той, якого не постачає жоден пакет | пропозиція **`needs_target`**, `target_path` порожній, модель не запускається |

Рядок `needs_target` — справжні докази з невідомим файлом: «Здоров’я → Радник» показує його з
причиною на картці, комірка цілі читається як `no target file — dismissing is the only transition`,
і є кнопка **Прибрати**. Прибрати — єдиний перехід, який він має: погодження
відхиляється, бо застосовувати нічого. Вибору цілі в цій фазі немає; якщо його
додадуть, текст тієї комірки й цей абзац зміняться разом. Він рахується як ВІДКРИТИЙ для інваріанта «один відкритий», тож
урок, який ніхто не може розмістити, не накопичує дублікатів рядків; прибирання звільняє слот, і правило
пропонує наново, якщо урок повторюється.

**Чого цикл робити НЕ може.** Гейт області шляхів і далі дозволяє рівно один змінений шлях, і для
пропозиції скілу цей шлях — `SKILL.md`. Сусідні файли скілу `resources/*.md`
у цій фазі недоторканні — дифф, що торкається одного з них, відкидається цілком із гейтом `path scope`, а не
підрізається. Моделі про це сказано в її промпті, і гейт забезпечує це в будь-якому разі.

**Одна відкрита пропозиція на ЦІЛЬ**, а не на ім’я (міграція `0074` замінює індекс з `0022`).
Агент і скіл можуть мати однакове ім’я, не зіштовхуючись; два уроки, спрямовані на той самий `SKILL.md`,
зіштовхуються, і другий відкидається. Підняття semver іде за пакетом, якому належить відредагований файл,
а для `plugins/core` додатково дзеркалиться в `metadata.version` маркетплейсу.

## 5. Життєвий цикл рекомендації

```
proposed ──Accept──▶ accepted ──(auto)──▶ adopted ──(auto, ≥7 d)──▶ verified
    │                    │
    └──Dismiss──▶ dismissed (30-day snooze, then re-proposed if still firing)
```

- **Прийняти** = «я діятиму за цим». Воно знімає **базовий знімок** метрики правила.
  Більше кнопка нічого не змінює — саме виправлення за вами.
- **Adopted** визначається автоматично, за типом цілі:
  - *agent* — файл промпту агента змінився (новий рядок `agent_versions` після
    прийняття; системний реєстр версіонує кожного агента за хешем вмісту). Ціль,
    відсутня в реєстрі (ситуативна мітка з реєстру делегувань), не має сигналу впровадження
    і перевіряється одразу з `accepted`;
  - *tool* — після прийняття створено увімкнене правило погодження, що покриває інструмент;
  - *process* — статус указаного рядка покращення змінився на done/closed/виконано;
  - *error_group* / *config* — виявного впровадження немає; вони йдуть прямо з `accepted`
    на перевірку.
- **Verified** вимагає ≥ 7 днів після впровадження, достатнього трафіку після зміни (пороги
  активності — відсутність даних ніколи не підтверджує) і ≥ 20 % відносного покращення проти
  базового знімка. Інакше картка лишається `adopted` з приміткою «вимірного покращення
  ще немає». Базові знімки версіонуються за метрикою: якщо метрику колись перевизначать, порівнювач
  зніме новий базовий знімок замість порівнювати несумісні числа.
- Доки іде відлік, чип статусу картки рахує дні до перевірки («перевірка
  через N дн.», потім «чекаємо на покращення ≥20 %») і показує базове значення метрики,
  її останнє спостережене значення й ціль, якої вона має досягти.
- Усі переходи захищені предикатами — прибирання, що перегнало запуск за 24 год, не може бути
  воскрешене, а API повертає 409 на суперечливі PATCH.

Запропоновані рекомендації рахуються у Вхідних (бейдж сайдбара, вкладка *радник*) і в
лічильнику `N open` вкладки «Радник».

## 6. Робота з ретро — плейбуки

### Щоденний цикл

1. Відкрийте вкладку *радник* у Вхідних (або «Здоров’я → Радник»), коли там є щось відкрите.
2. Розгорніть `evidence` на нових картках; за сумніву пройдіть за зразками id сесій.
3. **Прийміть** те, що виправлятимете, **приберіть** шум (він повернеться через 30 днів, якщо справжній).
4. Зробіть виправлення (правка промпту, правило погодження, домовленість, інфраструктура).
5. Система сама просуває картку до `adopted`/`verified`; згорнута
   секція Verified накопичує докази того, що зміни справді спрацювали.

### Закриття рекомендації щодо агента (розібраний приклад)

Першу бойову R2 (implementation-agent, 90 % невдалих запусків) закрили
так: запит до БД щодо таксономії помилок агента → найчастіший клас — порушення
шляхів worktree → Прийняти в дашборді (базовий знімок зроблено) → додати цільовий
розділ «гігієна помилок інструментів» у промпт агента → підняти semver плагіна, злити,
синхронізувати кеш плагінів → sysscan версіонує файл → наступний запуск радника автоматично переводить картку
в `adopted`. Перевірка порівнює частку невдалих запусків через тиждень.

### Живлення конвеєра уроків

Уроки існують, лише якщо задачі завершують **фазу 9**. Парсер очікує всередині
`phases/09-retrospective.md`:

- рядок таблиці метрик `| **Duration** | <est>h | <act>h | <var>% |` (комірки незалежно
  необов’язкові);
- секцію `## 💡 Lessons Learned` із записами `### Lesson N: <title>` — тіло до
  наступного заголовка, необов’язковий `**Action**: <one-line instruction>`;
- таблицю `## 📈 Process Improvements` (`| text | priority | owner | status |`) —
  рядки `{{placeholder}}` пропускаються; **оновлюйте `status` на `done`, коли покращення
  виходить**, і заради чесності, і тому, що R5 стежить за цією колонкою.

Шаблон лежить у
`plugins/core/templates/working/phases/09-retrospective.template.md`; потік tech-lead
пише його через скіл `session-closeout`, а `agent-work.sh complete` попереджає, коли задачу
архівують без нього.

### Імпорт результатів евалів

```bash
cd evals && npx promptfoo@latest eval   # створює results.json
swarmery evals-import --agent tech-lead path/to/results.json
```

Ідемпотентно для пари (suite, started_at); невідомі імена агентів — жорстка помилка з переліком

## 7. Довідник API

| Ендпоінт | Призначення |
|---|---|
| `GET /api/retro/agents?from&to&project` | рядки табелів + `main` + блок попереднього вікна |
| `GET /api/retro/friction?from&to&project` | інструменти з відмовами (`has_rule`), групи помилок, чекання погоджень |
| `GET /api/retro/lessons?from&to&project` | стрічка уроків (найновіші спершу, ліміт 100) |
| `GET /api/retro/lessons?group=1&…` | ТЕ САМЕ вікно, згорнуте за `norm_title`, найчастіші спершу |
| `GET /api/retro/tasks?from&to&project` | відхилення оцінок, цикли, вердикти делегувань (ліміт 200) |
| `GET /api/retro/recommendations?status=` | CSV-фільтр; типово `proposed,accepted,adopted`; `status=all` |
| `PATCH /api/retro/recommendations/{id}` | `{"status":"accepted"\|"dismissed"}`; лише дозволені переходи (422), конфлікт → 409; лише локальне походження |
| `POST /api/retro/advise` | запустити радника зараз; повертає `{proposed, updated, adopted, verified}`; лише локальне походження |

### `?group=1` — згруповане подання уроків

`group=1` (також `true`/`yes`/`on` або голий `?group`; `0`/`false` вимикає) зберігає вікно й
область проєкту без змін і міняє лише згортання, тож два подання ніколи не розійдуться щодо того,
що містив діапазон:

```json
{ "groups": [
  { "norm_title": "sync cache before build",
    "title": "Sync-cache before build",
    "tasks": ["2026-09-10-task-a", "2026-09-08-task-b", "2026-09-04-task-c"],
    "count": 3,
    "latest_action": "add it to the build skill" }
] }
```

Упорядковано за спаданням `count`, нічиї розв’язує `norm_title`, тож два виклики над незміненим вікном
повертають той самий порядок; ліміт 100 груп. `count` — це **різні задачі**, `title` і
`latest_action` беруться з найсвіжішого входження (`latest_action` — `null`, коли те
входження не мало рядка `**Action**:`), `tasks` — найновіші спершу. Рядки з порожнім
`norm_title` виключено — групування за маркером «ще не згорнуто» звалило б кожен неспоріднений
урок до 0070 в одну фальшиву групу з високим лічильником на вершині саме того подання, яке має показувати,
що повторюється. При `count ≥ 3` подання **Групувати за уроком** позначає рядок жовтим: це
той самий поріг, на якому спрацьовує R11.

- Міграція **0070** — `retro_lessons.norm_title` + `idx_retro_lessons_norm_title`: міжзадачна
  ідентичність уроку (R11, `?group=1`). `NOT NULL DEFAULT ''`; `''` означає «ще не згорнуто».
- Міграція **0072** — розширює CHECK `recommendations.target_kind` значенням `'skill'` (R11).
  Пронумерована **вище 0071 навмисно**: міграції застосовуються в порядку імен файлів, а 0071 перебудовує
  таблицю з повністю виписаним словником, тож розширення з меншим номером було б
  мовчки скасоване на свіжій базі без жодної помилки.
- Міграція **0102** — `operator_corrections` + `idx_operator_corrections_key (norm_key, created_at)`:
  реєстр операторських правок, який читає R14 (§4). `source` — словник CHECK, `ref` — типізований текстовий
  вказівник (без FK, за 0073), `norm_key` — згортання `NormalizeLessonTitle` тексту причини/after.
- Міграція **0074** — `agent_change_proposals.target_kind` + `target_path`, статус
  `needs_target` і частковий унікальний індекс «один відкритий» за ключем
  `(target_kind, COALESCE(NULLIF(target_path,''), agent))` замість `(agent)` з `0022`. Пронумерована
  **вище 0073** з тієї ж причини порядку імен файлів, що й 0072.
