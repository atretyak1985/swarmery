# Початок роботи

Swarmery — це дві речі, які виходять з одного репозиторію, і розуміння того, якої з них
ви торкаєтеся, убезпечить від плутанини надалі.

> [!NOTE]
> **Маркетплейс** — це набір плагінів Claude Code (агенти, скіли, команди й хуки), які
> встановлюють ваші проєкти і які працюють усередині ваших сесій Claude Code.
> **Центр керування** — локальний демон на Go із вбудованим дашбордом на React, який
> *спостерігає* за цими сесіями і дає вам вхідні, плани, метрики здоров’я й документацію
> на `http://localhost:7777`. Кожен із них можна запускати без іншого. Вони перетинаються
> лише через файли, які Claude Code і так пише на диск.

```stats
13 | плагінів у маркетплейсі | hot
89 | Go-пакетів у демоні
202 | маршрутів HTTP API
14 | документів на /docs
```

## Що таке swarmery

Маркетплейс постачає один вендор-нейтральний плагін **`core`** і дванадцять доменних
пакетів на вибір (`uav-pack`, `iot-pack`, `web-pack`, `infra-pack`, `lsp-pack`,
`claude-eng-pack`, `graft-pack`, `graphify-pack`, `architecture-pack`, `jira-pack`,
`accounts-pack`, `design-pack`). У плагіни не зашито нічого проєктного: кожен
споживач задає свою специфіку під час виконання через оверлей
`.claude/project.json` — саме тому той самий `core` працює і для флоту дронів,
і для інтернет-магазину.

Центр керування живе в `tools/swarmery/`. Це один бінарник — дашборд на React
зібраний і вбудований через `go:embed`, тож нічого не треба роздавати окремо
й не треба наглядати за другим процесом.

## Встановіть центр керування

```bash
git clone https://github.com/atretyak1985/swarmery.git
cd swarmery
bash scripts/install-swarmery.sh          # збирає один бінарник із вбудованим дашбордом
./tools/swarmery/swarmery serve           # слухає :7777
```

Переконайтеся, що він піднявся, і відкрийте дашборд:

```bash
curl -s http://localhost:7777/api/health  # → {"status":"ok",…}
open http://localhost:7777
```

Демон слухає `127.0.0.1` і не має автентифікації — за задумом це однокористувацький
інструмент лише для localhost. Не відкривайте порт назовні.

## Підключіть проєкт

Виконайте це з кореня проєкту, який хочете підключити:

```bash
swarmery onboard <project-slug> [pack ...]
```

Якщо бінарника ще немає у вашому `PATH`, двійник на чистому bash робить те саме:

```bash
bash <swarmery-repo>/scripts/init.sh my-shop web-pack
```

У будь-якому разі ви отримаєте два файли, і жоден із них не перезаписується, якщо вже існує:

| Файл | Що містить |
|---|---|
| `.claude/settings.json` | Реєстрацію маркетплейсу (`extraKnownMarketplaces.swarmery`), перелік увімкнених пакетів (`enabledPlugins`), блок `env` і заборони дозволів для `.env` / `secrets/**` |
| `.claude/project.json` | Ваш оверлей зі специфікою проєкту — репозиторії, головний застосунок, хмара, доменні терміни, скоупи комітів, увімкнені пакети |

Команда також створює простір імен у робочому просторі під
`$AGENT_WORKSPACE_ROOT/<slug>/`: `wiki/` і `workspace/` із теками
`working`, `archive`, `plans`, `specs`, `sessions`, `logs` і `metrics`. Саме
в цьому дереві живуть плани й артефакти задач — навмисно поза вашим репозиторієм із кодом.

Підключення з дашборду також реєструє теку як проєкт під введеним вами slug.
Є один виняток. Якщо swarmery вже бачив сесії в цій теці, проєкт **зберігає свій
наявний slug**, і кроки підключення про це кажуть. Slug — це ідентичність проєкту:
worktree для диспетчеризації називаються за ним, а сесії з цих worktree приписуються
проєкту через нього, тож перейменування на місці осиротило б їх.

**Налаштування → Проєкти за замовчуванням показує підключені проєкти.** Проєкт
вважається підключеним, коли має власний конфіг swarmery, а не просто лежить усередині
іншого підключеного проєкту. Це відсікає підрепозиторії мультирепозиторної
«парасольки», які носять скопійований `settings.json`. `/`, `$HOME` і корені
підключення ніколи не вважаються таким батьківським проєктом, тож увімкнений на рівні
користувача core не ховає ваші проєкти. Рішення ухвалює демон (поле `onboarded`
у `GET /api/projects`).

Зніміть позначку **лише підключені**, щоб побачити все. Коли фільтр ховає всі проєкти,
сторінка каже, скільки їх приховано, і пропонує зняти позначку. Проєкт System
лишається видимим. Вибір
запам’ятовується в браузері.

Маркетплейс ніколи не потрібно додавати вручну: запис цієї реєстрації у
`.claude/settings.json` — частина того, що робить підключення, тож окремого кроку
«додати маркетплейс» немає.

Схема оверлею позначає обов’язковими лише три поля — `name`, `codePath` і
`enabledPacks`, — а скелет лишає маркери `TODO` для тих, які варто
заповнити:

| Поле | Значення |
|---|---|
| `name` | Slug у kebab-case; також ключ робочого простору і `AGENT_PROJECT` |
| `codePath` | Абсолютний шлях до кореня коду проєкту |
| `enabledPacks` | Доменні пакети, які вмикає цей проєкт (дзеркало `enabledPlugins`) |
| `repos` | Шляхи до коду відносно робочого простору, у яких агентам дозволено шукати |
| `mainApp` / `apps` | Головний застосунок і його сусіди |
| `stack` / `domainTerms` | Технології за областями та іменники, якими мають користуватися ваші промпти |
| `commitScopes` | Скоупи, дозволені у ваших conventional commits |

> [!WARNING]
> Зміни плагінів набувають сили в **наступній** сесії Claude Code, а не в поточній.
> Після підключення відкрийте нову сесію і прийміть запит довіри до маркетплейсу
> swarmery.

## Запустіть центр керування

З `tools/swarmery/`:

| Команда | Що робить |
|---|---|
| `make build` | Знімок документації → бандл vite → `go:embed` → один бінарник `./swarmery` |
| `make dev` | Демон на Go плюс dev-сервер vite, який проксіює `/api` на `:7777` |
| `make test` | `go vet ./...`, потім `go test ./...` |

Запуск `./swarmery serve` вручну тримає демон на передньому плані — так найзручніше
спостерігати за ним, поки ви освоюєтеся. Коли захочете, щоб він працював постійно,
`./swarmery install` копіює бінарник у `~/.swarmery/bin/swarmery` і реєструє його
в launchd (macOS) або `systemd --user` (Linux), щоб він стартував разом із машиною;
відтоді `make install` перезбирає, підміняє цю копію й перезапускає сервіс.

Демону не потрібне інструментування, бо він читає те, що Claude Code і так пише:
JSONL-транскрипти сесій у `~/.claude/projects/`, за якими він стежить через
`fsnotify` і періодичне пересканування, і індексує їх у SQLite у `~/.swarmery/swarmery.db`.
Інше місце задає `SWARMERY_PROJECTS_ROOTS`; порт змінює
`SWARMERY_PORT`.

## Перемикачі пакетів і провізіонування

Щоб увімкнути пакет, не треба правити JSON руками. У дашборді відкрийте проєкт
і скористайтеся перемикачами плагінів у його **Налаштуваннях** (`/p/<slug>/settings`) або в
**Система → Плагіни**. Перемикач робить лише точкове злиття у
`.claude/settings.json` цього проєкту — спершу пише `settings.json.bak` і
відмовляється перезаписувати файл, який не може розібрати. `core` увімкнено завжди.

Увімкнення пакета також ставить у чергу **задачу провізіонування** — справжній рядок
у базі SQLite демона, а не стан у горутині. Демон виконує її у власному процесі:
оновлює індекс маркетплейсу, встановлює пакет, а для пакетів, які оголошують крок
генерації, створює артефакт. Сьогодні такий крок оголошує лише `architecture-pack`;
решта пакетів лише встановлюються.

Оскільки задача — це рядок, перезапуск ніколи не губить її з поля зору, але й не
відновлює: усе, що було в польоті, позначається як збій із повідомленням `interrupted by daemon
restart`, тож ви бачите, що сталося, і свідомо перезапускаєте.

> [!TIP]
> Якщо перемикач начебто нічого не змінює, перевірте, чи немає `.claude/settings.local.json`,
> який закріплює той самий плагін у протилежному значенні — у сесіях він має пріоритет
> над `settings.json`. Дашборд повертає попередження, коли це виявляє.
>
> Якщо перемикач відхиляється одразу, демон запущено без
> `SWARMERY_ONBOARD_ROOTS`. Ця змінна — список тек, під якими дашборду дозволено
> писати файли `.claude/`, і запис перемикачів плагінів також під це підпадає.

## Ваша перша сесія

Запустіть сесію Claude Code у підключеному проєкті й дайте їй попрацювати кілька
хвилин. Потім погляньте на дашборд:

- **Сьогодні** — що відбувається наживо і що чекає на вас.
- **Сесії** — кожен транскрипт, наживо, з обліком вартості й токенів.
- **Плани → Дошка** — картки, зафіксовані з TODO-пунктів ваших сесій, які чекають
  на доріжці «Вхідні» дошки.
- **Плани → Плани** — документи фаз і їхній прогрес, прочитані просто з робочого
  простору.
- **Документація** — ця сторінка.

[Посібник із дашборду](guide-dashboard.md) проводить усіма десятьма місцями в сайдбарі.

Зафіксована картка — це *пропозиція*, а не зобов’язання. Ось увесь шлях, який картка
може пройти, щойно ви її приймете:

```figure card-lifecycle
```

[Посібник із планів](guide-plans.md) докладно описує кожну доріжку дошки, гейти допуску
й виходи з рев’ю.

## Шпаргалка

| Шлях | Чим керує |
|---|---|
| `.claude/settings.json` | Реєстрація маркетплейсу, увімкнені плагіни, env, дозволи |
| `.claude/settings.local.json` | Локальні для машини перевизначення — мають пріоритет над `settings.json` |
| `.claude/project.json` | Оверлей зі специфікою проєкту, який агенти читають під час виконання |
| `.claude/agents/`, `.claude/templates/` | Локальні компоненти проєкту; збіг імені перекриває компонент плагіна |
| `~/.claude/projects/` | JSONL-транскрипти, які індексує демон |
| `~/.swarmery/swarmery.db` | База SQLite демона |
| `~/.claude/plugins/cache` | Звідки насправді завантажуються увімкнені пакети — ніколи не з вашого checkout |

| Змінна середовища | За замовчуванням | Значення |
|---|---|---|
| `AGENT_PROJECT` | — | Slug проєкту; ключ простору імен у робочому просторі (бік плагінів) |
| `AGENT_WORKSPACE_ROOT` | `$HOME/swarmery-workspace` | Корінь репозиторію робочого простору (бік плагінів) |
| `SWARMERY_WORKSPACE_ROOT` | `$HOME/swarmery-workspace` | Двійник попередньої для демона |
| `SWARMERY_PORT` | `7777` | Порт дашборду і API |
| `SWARMERY_PROJECTS_ROOTS` | `~/.claude/projects` | Звідки читаються транскрипти |
| `SWARMERY_ONBOARD_ROOTS` | не задано | Батьківські теки, під якими дашборд може писати `.claude/`; якщо не задано — підключення *і* перемикачі плагінів вимкнені |
